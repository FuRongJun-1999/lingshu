# 真值维护——前提被推翻时下游结论自动撤回（v0.1，叠在证据账本 #430 上）

> 状态：提案（默认关闭，`LINGSHU_TMS=1` 或 `enable_tms()` 开启，隐含启用证据账本）。新增 `lingshu/core/tms.py`。

## 1. 问题
证据账本让单个命题的置信度由它自己的证据推导。但推理产物「因为 P1、P2，所以 C」在 P1 被反证推翻后保持原值，
`recall_with_evidence` 照样把 C 当事实交给宿主——前提死了，结论还活着。这是幻觉的另一条来路。

## 2. 模型（JTMS 式，白箱 · 确定性 · 零 LLM）
- 依据：`add_justification(结论, [前提…])`，前提合取；同一结论多条依据为析取。存 `justifications` / `justification_premises` 两表。
- 信念：
  - own(n) = 账本对 n 自身证据推导的置信度与状态；
  - jsup(c) = max_依据 min_前提 belief(p)；
  - belief(c) = own(c)（无依据，或 c 已被 ≥2 个独立外部来源佐证）；否则 min(own(c), jsup(c))。
  - **只撤回、不放大**：前提再可靠也不替结论增信（推导不是证据）。
- 撤回：jsup(c) < 0.3（账本的 REFUTED_BELOW）且 c 未被独立佐证 ⇒ 状态 `undermined`（前提已被推翻），列出推翻它的前提；
  `recall_with_evidence` 默认像对待 refuted 一样剔除。
- 传播：账本 `record()` 后回调 → 取下游闭包 → 以各自 own 为初值 Gauss-Seidel 迭代到不动点（值域有限，≤|闭包|+1 轮；环可处理）
  → 写回 `nodes.confidence`，使既有读路径看到同一个值。前提恢复后结论随之恢复。

## 3. 实测（构造场景）
随机推理 DAG：300 条基础事实（各 2 源佐证）、600 条结论（每条 1–3 个前提，30% 有两条依据，2% 前向 / 成环依据），
推翻一部分基础事实（每条记 8 个独立反证）。真值按不动点求：结论应撤回 ⇔ 它的每条依据都含应撤回的前提。

| 推翻比例 | 应撤回 | 仅证据账本：撤回召回 / 误撤 | 账本 + TMS：撤回召回 / 误撤 | 每条证据传播耗时 |
|---|---|---|---|---|
| 10% | 107 | 0% / 0 | **100% / 0** | 2.3 ms（关时 0.09 ms） |
| 30% | 302 | 0% / 0 | **100% / 0** | 2.4 ms |

如实说明：这组数据验证的是**实现与规格一致**（真值与 TMS 用同一套语义），不是「推理更准」。价值在于：
没有 TMS 时，这 107 / 302 条结论在推翻发生后仍以原置信度被召回；有 TMS 时一条不漏地标为「前提已被推翻」，
且没有误伤仍有依据的结论。规模扩展读数见 PR 正文。
