# 检索不刷新近因——切断 search → last_access → recall 近因的自增强回路（v0.1）

> 状态：提案（默认关闭，`LINGSHU_RETRIEVAL_NO_TOUCH=1` 开启）。只改「检索命中时是否写 last_access」，不改打分公式。

## 1. 问题
`EngineFacade.recall` 打分 = 0.5·sim + 0.3·importance + 0.2·recency，recency = 1/(1+距 last_access 的天数)。
而 `LayeredStore.search_content`（recall 的候选来源，limit=50）对**每个返回节点**调 `increment_access`，
把 last_access 改成「现在」。于是：

1. 一次查询会把 50 个候选（多数与本问无关）的近因刷成 ≈1.0；
2. 下一次查询里，这些节点仅因「上次被搜到」而多拿至多 0.2 分；
3. 新写入、尚未被搜到过的记忆反而吃亏——**更正 / 更新类信息最怕这一点**。

检索 ≠ 使用 ≠ 强化。近因应该反映记忆**最近一次被真实确认**的时间，而不是最近一次出现在候选池里。

## 2. 改动
- `LayeredStore._retrieval_touches_recency()`：开关开时返回 False。
- `increment_access(node_id, touch=True)`：`touch=False` 时只 `access_count += 1`，不写 last_access。
- 检索路径（`search_content`、`semantic_search`）按开关传 `touch`。
- **不动**的路径（它们是真实强化事件，照常刷新 last_access）：M5 重复观测命中、
  `update_node_confidence`（验证复核）、巩固复述（`consolidate` 内 rehearsal）。
- access_count 仍计数，`decay_cycle` 的「access_count==0 且长期未访问」判据语义不变。

## 3. 实测（真实引擎，读数可由 `bench/bench_retrieval.py` 复现）
| 场景 | 改前 | 改后 |
|---|---|---|
| 知识更新：200 个实体·属性，旧值 200 天前写入并被问过 1 次，再写新值；recall top-1 为新值（LIKE 能命中的问法，原检索路径） | 0.69 | **1.00** |
| 同上，自然语言问法 + FTS5 路径（PR #FTS） | 0.62 | **1.00** |
| 同上，自然语言问法，原检索路径 | 0.00 | 0.00（原路径根本取不到新写入节点，见 #35，与本改动无关） |
| hive-memory-bench 切B，recall top-10，时间戳在过去 1–365 天随机打散，连续 5 轮查询流：证据保留 / 块级命中（原路径） | 17.6 / 62.7 | 15.8 / 64.9 |
| 同上（FTS5 路径） | 24.4 / 69.6 | 23.6 / 69.2 |

如实说明：
- hmb 读数小幅下降不是退化信号，而是暴露了旧行为的另一面：第 1 轮查询后，切B 的 203 块几乎全被刷成「刚访问」，
  近因分量对所有块≈常数，等于**被抹掉**；关掉刷新后近因恢复为（这里随机构造的）写入时间，于是成了噪声。
  在近因真有信息量的场景（知识更新）里收益是 +31~38 个百分点。
- 「知识更新」是构造场景：新旧句式取自同一模板池、sim 接近，近因是决胜项。真实对话里差距会更小。
- 写入用 skip_dedup=True：只差数值的新旧事实会被 M5 合并（#142），那是另一个问题（见矛盾感知提案）。
