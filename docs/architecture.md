## 二、聚合原则（四条硬纪律）

1. **组合，而非复制**——脑核不做 vendoring/fork：以依赖引入，版本升级走包管理器；
   身体件不做原地链接：筛选后**导出副本**在本仓固化（导出时上游为非公开仓；**已导出完毕，现为本仓自有面**）。
2. **单向引入**——上游是真源；本仓的修改若要回流，走上游仓的纪律流程（不得本仓直改再反向同步）。
3. **逐件筛选**——任何身体侧件入仓前，逐件过：
   - **内容政策清单**（无凭据 / 无本机路径字面量 / 无个人隐私 / 无第三方受限内容）；
   - **隐私清单**（不含私有内容资产：记忆数据、私有模块名、私有算法细节）；
   - 筛选记录随件入档（`docs/intake/` 登记表）。
4. **干净历史**——本仓不迁移任何上游的 git 历史（上游历史含非公开提交）；
   首次引入即初始提交，来源以上游仓+版本号标注。

## 六、边界章程（不许违反）

- 记忆数据（认知图真源、会话记录、任何 `data/`）**永不入本仓**；
- 凭据、令牌、密钥（含示例性真值）**永不入本仓**；
- 非公开内容模块（外部上游仓的非公开线，若有）**永不入本仓**，不得被引用或概括；
- 本仓所有文档不写本机绝对路径字面量。

### 6.1 锚点层写入面：一律 fail-closed（维护者 2026-10-10 裁定）

**锚点层是不可变声明层，属极度重要的信息**——其写入面**一律 fail-closed**：

- 进入不可遗忘共享层的**唯一**入口是 `SpacetimeMemoryEngine.register_external_anchor`
  （`lingshu/core/core.py`），其 `ANCHOR_KINDS` 是**封闭白名单**，恰为
  `pre_access_stance` / `introspection` / `external_calibration` 三项；
- 白名单之外的 kind 一律 `ValueError`，**不做**静默降级、**不**自动放行新 kind；
  新增 kind 属设计取舍、须经裁定，不得由实施者顺手放宽；
- 该入口另带设计者密钥闸（未配置/不匹配即 `PermissionError`），与「提案→复核→终裁」
  同款 fail-closed 取向。

> **裁定出处**：维护者 2026-10-10 裁定（对应公开 issue「版本迭代记录无写入入口：
> `ANCHOR_KINDS` 只认三种」）——「关于锚点层确实是极度重要的信息，需要收紧」。
> 即维持三 kind 白名单、不放行第四种。
> **守卫**：`tests/test_issue329_anchor_kinds_guard.py`（钉死取值 + 防第二份硬编码 +
> 写入门槛 + 记录惯例单一真源）。

### 6.2 导入期宿主纯净性：受控面 = 启动期快照（维护者 2026-10-10 裁定）

白名单组件的**受控面**（允许被解析到的面）由**进程启动时刻**确定，或由显式配置
`LINGSHU_COMPONENT_ROOT` 声明，**不随判定时的 cwd 变化**；**相对路径** `sys.path`
条目不得因「恰好当前 cwd 在其目录内」而被当作受控面。

> **裁定出处**：维护者 2026-10-10 裁定（对应公开 issue「导入期宿主纯净性」）——
> 采 **D-2**（启动时快照／显式受控面，不吃 cwd 判定），否掉「按判定时 cwd 清洗」的
> 现状口径。
> **守卫**：`tests/test_issue288_host_purity_d2.py`（冻结性 + 相对条目不入选 +
> 正对照：绝对路径合法受控目录仍被接受）。

### 6.3 角色与信任边界：角色是实例属性，不是安全边界（维护者端裁定 2026-10-16）

**裁定**：`Role`（`lingshu/core/core.py`）的**唯一真源是本进程构造参数**（默认
`Role.PRIMARY`），既不落库、也不与库级凭据绑定（`export_all` 节点键集与
`engine_meta` 键集均无 `role`）。⇒ 角色闸**拦的是「角色误用 / 协作分工」，不是
「谁能读这个库」**。**本仓不做单点收口**——本件只把这条边界**写明**（docstring +
本节），收窄取向归设计者。

| 面 | 是否在角色闸作用面内 |
|---|---|
| 非 PRIMARY 实例写共享层（锚点层 / 结构层，`SHARED_LAYERS`） | **在**（拦） |
| 共享层端点的边写入（#234 / #674）、`import_all` 导入含共享层行（#586）、终裁固化提案（#586） | **在**（拦） |
| 同一进程内**主动自建属主实例**（`role=Role.PRIMARY`、同一 `db_path`）、同进程直改 `store.role` | **不在**（放行） |
| **直接打开 `db_path` 写库**（如 `sqlite3.connect(db_path)` 改 `nodes` 行） | **不在**（放行，且**无需**伪造角色即可越过角色闸与密钥闸） |

**为什么归「设计面」而非「漏了一个闸」**：末行读数证明，能在同进程拿到 `db_path`
的代码**不需要**伪造 `Role` 就能直接改库 ⇒ 任何「库级 / 实例级」的收窄（例如
「角色绑库级凭据」「同 `db_path` 互斥」）在**同进程**威胁下都不成立。这是**威胁模型
边界**问题，与密钥面（`verify_designer` 的同进程声明）**同构**。

**归属（★口径如实标注）**：同进程可信性属**设计级**事项，归属与密钥面同款 ——
见 `verify_designer` docstring「同进程可信性属**设计级**事项，待 D-007 后续裁定」
（公开 issue `#156`）与 `docs/plans/待裁清单_v0.1.md` 附-C ⑦ 的 `#156` 深修路线。
该 ⑦ **原文逐字只写「架构面让不可信代码不与密钥同进程」——只写密钥面、未写角色面**；
本条与它**同族 / 同构**，**不是**「⑦ 已覆盖角色面」。本取向的依据是上述实证读数
（同进程直连 `db_path`），不是对 ⑦ 原文的扩张解释。

**仓内既有同向表述（本节只是写明，不新增取向）**：
- `docs/plans/场景推演整合_v0.1.md`：「本层的角色/会话过滤是消费作用域，**不是身份
  认证边界**」；
- `lingshu/core/core.py` 的 `add_node` docstring：只自称「多角色**写权限边界**」。

**若日后要收窄**（归设计者，本仓不动）：落点＝**共享层写面统一收口**（单一
`assert_role_can_write(layer)` 真源，覆盖 `update_node_confidence` /
`update_node_importance` / `set_meta`），可与公开 issue `#780` 的同类建议**同笔**
设计。对照先例：`import_all` 的**库外凭据闸**（设计者密钥）对进程内角色伪造**免疫**，
是仓内既有的「库外凭据面」样本。

> **裁定出处**：维护者端裁定（2026-10-16，公开 issue `#779` 定性收口；依设计者
> 2026-10-14 授权口径「与理论冲突的合并归设计者，其余归灵枢设计者裁决」——本条经
> `git grep` 核实 `docs/theory/**` 无角色/信任边界表述，**不属理论冲突**）。
> **落地**：`lingshu/core/core.py` 的 `Role` docstring（同一笔提交）。
> **守卫**：本件为纯文档声明，**不新增测试件**（既有角色闸守卫

### 6.4 实体标注与检索边界：`entity_id` 是名词挂接，不是隔离边界（维护者端裁定 2026-10-17）

**裁定**：节点级 `entity_id`（`STNode` 字段，v1.7「名词挂接」面）是**标注**，不是
**数据隔离边界**。⇒ 异实体（含**另起进程**的实例）经 `recall` / `search_content`
可原样取回彼此记忆，属**设计现状**，**不是缺陷**；本仓**不**在检索面按实体过滤。

| 面 | 现状读数（基线 `origin/main` 实读） |
|---|---|
| 检索面引用数 | **0** —— `LayeredStore.search_content`（LIKE 路径）的 WHERE 只由 `layer IN (…)` 与 LIKE 片段构成；`SpacetimeMemoryEngine.recall` 的候选集与终排无该列；FTS 路径 `FTSIndex.candidates` 同样无；`lingshu/core/retrieval.py` 内该字段引用数 **0** |
| 读侧消费点 | 仅**展示面**两处（均非过滤 / 鉴权）：`render_semantic_cube_3d` 的轨迹过滤、`query_by_semantics` 的实体名加分 |
| 理论面 | `docs/theory/**` 内「实体隔离 / 实体边界 / 多租户 / 租户」**0 命中**——仓内无任何章节规定它是隔离边界 |
| 仓内文字说明 | 仅字段注释一行（`# v1.7：名词（实体挂接）`）＋ 世界模型 `configure_action(entity_id, …)` 的同名参数（与记忆节点无关） |
| 写入面生产者 | 默认形态下 `entity_registry` 未装 ⇒ 该列**全为 NULL**（`ingest_frame` 的解析分支不执行；`add_perception(entities=[…])` 只落 `ent:<id>` 标签，不落该列） |

**为什么不做「按调用方实体过滤」**（三条，逐条独立成立）：

1. **会误伤跨实体共享知识**——共享层（锚点层 / 结构层）语义即「跨实例同步、不可遗忘」，
   按调用方实体过滤会把共享层一并切掉；
2. **缺一格前置**——**调用方实体从哪里来**：引擎构造器只有 `identity`（进 `SelfModel`）
   与 `role`（进 `LayeredStore`），`nodes` 表也无属主 / 实例列；
3. **属语义取向变更**——不是「补一个漏掉的闸」，须经裁定，不得由实施者顺手收窄。

**同款口径先例**（本节只是把现状**写明**，不新增取向）：

- §6.3：`Role` 是实例属性，**不是安全边界**（同一威胁模型边界）；
- `docs/plans/场景推演整合_v0.1.md`：「本层的角色/会话过滤是消费作用域，
  **不是身份认证边界**」。

**若日后要升格为隔离边界**（归设计者，本仓不动）：须**同时**定「调用方实体来源」
与「共享层跨实体可见的例外口径」，落点＝引擎构造参数 ＋ 检索入口签名，宜与 §6.3
的共享层写面收窄**同笔**设计。

> **裁定出处**：公开 issue `#766`（报告人自陈「两种裁定都会改变修法」，先只报事实
> 与读数）＋ 本端三条独立复核（理论面 / 全仓声明面 / 检索模块引用数）**均未推翻**本方向。
> **落地**：`lingshu/core/core.py` 的 `STNode.entity_id` 处注释（同一笔提交；该笔
> **只增注释**，剥掉全部 docstring 后 `ast.dump()` 与 `origin/main` 逐字相同）。
> **守卫**：本件为纯文档声明，**不新增测试件**（既有检索面守卫不覆盖「实体维度」——
> 该维度**刻意不设**检索闸：它不在本仓的边界作用面内，设闸会造成「实体已是隔离
> 边界」的假象）。
