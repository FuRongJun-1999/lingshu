# PR 审核细则 v0.1（验证者用）

> 目的：让每一件进入合并队列的 PR，都过「**技术审（验证者）＋ 理论核（本项目）**」两道闸。
> 验证者做技术审并给出结论；**最终确认与合并由本项目执行**。

---

## 一、你的产出（每件一条，直接贴到该 PR 线程）

1. **判定**：建议采纳 ／ 改编采纳（写明改编点与理由）／ 不宜采纳（写明理由）／ 无法判定（写明缺什么）
2. **复现**：你在**当前 main** 上的独立读数（改前 vs 改后），与作者声明**逐项对照**；不一致处直接标出（不一致不等于作者错——以你的实测为准并写明差在哪）
3. **补丁评估**：改动面（文件＋函数/符号；**不要写行号锚**，行号会漂）／是否最小／副作用面（既有测试与调用点）
4. **守卫**：该 PR 自带的测试**能不能鉴别**（判据：把修复回退 ⇒ 断言必须红）；不能鉴别就指出该补什么断言
5. **存疑**：拿不准的写明「存疑」与缺的信息；**不要猜**

## 二、技术审硬判据（不满足 ⇒ 「需改后重提」）

- **基线对齐**：补丁须能干净应用到当前 main；不能应用就注明与哪一笔冲突
- **可复现**：必须有改前/改后读数对照；「看起来对」不算
- **最小性**：不夹带与问题无关的改动（格式/重命名/重构请另开 PR）
- **不掩盖**：**禁止**通过放宽/删除断言、改阈值、跳过用例来「变绿」
- **守卫**：行为变更必须带可鉴别断言（回退即红）
- **回归**：受影响面的既有测试须通过，并说明你跑了哪些

## 三、理论核（由本项目执行；你可在评审里先标出「是否涉及」）

以下为本项目判据，请审时逐条对照并标注涉及项：

1. **白箱**：条件显式、判据可读；不引入不可解释的黑盒分支
2. **不猜测**：结论须有证据（读数/锚点）；推断须标注为推断
3. **边界诚实**：修不完的部分显式标注，不静默降级、不静默失败
4. **判据外置**：行为规则以可检验的断言落地，而非注释里的承诺（「宣称 vs 实现」类缺陷的主防线）
5. **不做未裁定的设计变更**：架构级取舍由本项目裁定，PR 不夹带设计变更

## 四、边界（关键）

- 你的审是**强建议**：**最终确认与合并由本项目做**（我们负责理论核与对外发布）
- 你可以要求作者补：更短的最小复现、读数对照、守卫断言
- 遇到**口径争议/设计取舍** ⇒ 在评审里标注 `needs-owner-decision`，交本项目裁定
- **你不合并**：即使建议采纳，合并由我们执行（合并后按惯例致谢并在线程交代）

## 五、流程与标签

| 环节 | 谁做 | 标记 |
|---|---|---|
新 PR 到达 | 本项目 | `needs-verifier-review`，并请验证者审 |
技术审完成 | **验证者** | 结论贴线程；有标签权限则改 `verifier-approved` / `verifier-rejected` |
理论核 + 边界确认 | 本项目 | `confirmed-for-merge` ⇒ 合并；未过则回帖说明理由 |
争议/设计取舍 | 本项目裁 | `needs-owner-decision` |

## 六、体例参照

- 技术审的体例可参照本仓已核验件的回复（issue #1／#2／#4 的处理帖）——判定在前、读数对照在中、处置与边界在后；
- 本仓近期已走完一轮「外部报告 → 独立核验 → 逐条回帖」的全流程（当晚 10 件），核验报告的格式（判定／读数对照／根因锚／处置／存疑）即本细则期望的产出形态。
