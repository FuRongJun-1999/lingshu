## 1. 产品定位与范围

### 1.1 一句话

**把「悬赏」和「项目管理」合成一件事**：发布者把一个活儿拆成里程碑发出来，任何人（或 agent）可以接，
在期限内按里程碑交付，发布者验收后系统分配声誉与赏金，并生成**完成码**供双方线下结算。

### 1.2 做什么

| 面 | 内容 |
|---|---|
| 任务发布 | 标题、描述、难度、总赏金（¥）、期限、**自由设计的里程碑** |
| 认领 | **多人可接同一个任务**；个人接或团队接；受等级额度限制 |
| 交付 | **证据包**（文字 + 文件 + 链接）；提交入口在**任务页**，不在个人页 |
| 验收 | 逐里程碑验收；退回返工；轮次上限 |
| 决策 | 到决策点时发布者选人、付阶段性赏金、继续或结束 |
| 分配 | 发布者自由分配赏金给多个主体，**审核完之后仍可改** |
| 结算 | 每个被分配主体生成**一个完成码**；发布者**看不到码**，只能填码核销 |
| 项目管理 | 变更单（改赏金/期限/里程碑）、中途取消、补偿金、看板 |
| 声誉 | 系统唯一裁决；个人等级 1–10；团队等级 1–30 |
| 榜单 | 声誉榜 + 累计赏金榜，各做**永久榜**与**自然月榜** |
| 团队 | 建队、邀请、踢人、转让、解散；团队接单；队长分配 |
| Agent | OpenAPI / CLI / MCP 三种接入；API Token 全权可吊销 |
| 管理 | 管理组可改一切；可封禁；全量审计日志 |

### 1.3 明确不做（本期）

| 不做 | 原因 |
|---|---|
| **资金托管 / 在线支付** | 定。MVP 不碰钱，只发码；钱由双方线下结 |
| **接 GitHub / 读 PR / 托管代码** | 定。只做证据包交付 |
| **记录 PR 元数据** | 定。不接外部代码托管 |
| L3 项目包 / L4 任务依赖 | 定。**留接口不实现**（见 §11） |
| 邮箱验证 / 找回密码 | 定。MVP 只有用户名 + 密码 |
| 发布者以用户身份登录排障 | 定。MVP 不做 |
| 团队榜 | 定。不做 |

### 1.4 与参考站（ClawHunt）的关系

我们**抄它的机制，不抄它的商业模式**。抄的四条（读它 OpenAPI 得出，非猜测）：

1. **allowed-actions 协议** —— 服务端告诉前端「你现在能做哪些动作」，前端零判断（§5.3）
2. **变更单一等实体** —— 改需求走变更单而不是直接改字段（§4.2）
3. **验收标准结构化** —— 发布时必须写可复核的验收条目，否则发不出去（§4.1）
4. **私密对象不泄露存在性** —— 不存在的 ID 与无权限的 ID 返回**完全一样**的响应（§8）

**不抄**：它的资金托管、平台抽成、双向竞标定价。我们**没有钱在系统里**。

## 2. 总体架构

### 2.1 技术选型（**定**）

| 层 | 选型 | 为什么是它 | 为什么不选别的 |
|---|---|---|---|
| 语言 | **Python 3.12** | 与现有工作区一致 | — |
| 框架 | **Django 5.x** | 本平台是 **CRUD 密集的管理系统**，Django 的 Admin、权限、迁移、ORM 全部白送 | FastAPI 唯一优势是异步高并发，本平台用不上，且要自己写后台 |
| API 层 | **django-ninja** | FastAPI 式类型标注 + **自动 OpenAPI**，直接吃 Django ORM | DRF 更重、样板更多 |
| 数据库 | **PostgreSQL 16** | 关系型为主 + 里程碑配置用 **JSONB**；中文全文检索可扩展 | SQLite 单写者、MySQL 的 JSON/CTE 更弱 |
| 缓存/队列 | **Redis 7** | 限流计数、月度榜缓存、后台任务队列 | — |
| 后台任务 | **Huey** | 轻量、纯 Python、够用（超时扫描、月度榜、码过期） | Celery 太重 |
| 前端 | **Django 模板 + HTMX** | **不引入第二门语言**；交互由服务端渲染片段完成 | React/Vue 要多一套构建链（本期不做 UI，见 §7.0） |
| 容器 | **Docker Compose** | 定。一键起全套 | — |
| 反向代理 | **Nginx** | 生态最大、以后加限流/CDN 方便 | Caddy 更省事（§9.3 给替代配置） |
| 部署 | Linux（Ubuntu 22.04+） | 定 | — |

**库清单（精，不多——每个都必须有用）**：

| 库 | 用途 | 不装它的后果 |
|---|---|---|
| Django | 框架 | — |
| django-ninja | API + OpenAPI | 手写 OpenAPI，agent 接入要另写文档 |
| psycopg[binary] | PG 驱动 | — |

| Pillow | 头像处理 | 团队/用户头像 |
| argon2-cffi | 密码哈希（Django 内置支持） | 默认 PBKDF2 也可，装上更好 |

### 2.3 三条不可违反的架构原则（**定**）

> 这三条是硬约束，写代码时不许绕过。违反即评审不通过。

**原则一：判定在服务端，且必须走纯函数。**
所有状态迁移与权限判定写成**无 IO 的纯函数**：入参是数据（当前状态 + 动作 + 执行者 + 时间），出参是裁决（通过/拒绝 + 目标状态 + 理由 + 副作用）。
好处：可以喂夹具单测，可以做**定点变异自证**（注入必失败 ⇒ 断言必红并点名）。

**原则二：前端不做状态判断。**
前端调 GET /api/tasks/{serial}/allowed-actions 拿到「你现在能做哪些动作」的列表，**只渲染，不推断**。
按钮显示与否、能不能点，全部由服务端下发。前端被改烂也只能发出请求，改不了结果。

**原则三：不可信输入一律当作不可信。**
评论、文件名、用户输入、agent 请求体，全部按不可信处理。
（前车之鉴：某同类实现在评论里埋一段 HTML 注释当作权威状态，任何人贴一行伪造标记就能锁定他人任务、给任意人刷负分。本设计**不存在**"客户端写入的权威记录"——权威只在数据库。）

### 3.2 状态机

#### 3.2.1 任务状态（Task.status）

~~~
        draft ──publish──▶ open
                            │
                            │ 有人认领
                            ▼
                        claimed ◀───────────┐
                            │               │ 有人认领
                            │ 首个提交       │
                            ▼               │
                       in_progress ─────────┘
                            │
              ┌─────────────┼──────────────┐
              │             │              │
   到达决策点 │      全部里程碑完成        │ 发布者中途取消
              ▼             ▼              ▼
         reviewing ───▶ delivered      cancelled
              │             │
              │             │ 发布者分配
              └────┬────────┘
                   ▼
               allocated
                   │
                   │ 所有完成码核销完毕
                   ▼
                closed

旁路状态：expired（到期自动处理，见 §4.1.5）、disputed（争议，MVP 只记录不阻断）
~~~

| 状态 | 含义 | 谁能推动 |
|---|---|---|
| draft | 草稿，未公开 | 发布者 |
| open | 公开可认领 | 发布者发布 |
| claimed | 有人认领，进行中 | 接赏者 |
| in_progress | 已有提交 | 接赏者 |
| reviewing | 到达决策点，等发布者裁决 | 发布者 |
| delivered | 全部里程碑完成，待分配 | 发布者 |
| allocated | 已分配，码已生成，待核销 | 发布者 |
| closed | 全部码核销完，正常结束 | 系统 |
| cancelled | 中途取消，已付补偿金 | 发布者 |
| expired | 到期无人交付（终态，可复制重发） | 系统 |
| disputed | 争议中（旁路标记，不改变主状态） | 当事人/管理组 |

#### 3.2.2 认领状态（Claim.status）

~~~
active ──withdraw──▶ withdrawn          主动放弃（不扣声誉）
   │
   ├──expire──▶ expired                 超时未交付（扣声誉）
   │
   ├──select──▶ selected                被选中（继续做 / 或直接完成）
   │
   ├──reject──▶ rejected                落选（+难度声誉补偿）
   │
   └──complete──▶ completed             正常完成并结算
~~~

#### 3.2.3 完成码状态（CompletionCode.status）

~~~
issued ──redeem──▶ redeemed       发布者填码核销成功
   │
   └──expire──▶ expired           30 天未核销，任务自动关闭（发布者记"未核销"留痕，不扣声誉）
~~~

### 3.4 规则细则

#### 3.4.1 用户名规则（**定**）

- 长度 **2–20 字符**
- 允许：**中文**、字母、数字、下划线 _、连字符 -
- **大小写不敏感**：Alice 与 alice 视为同一人（存 username_cf = username.lower() 做唯一约束，显示保留原样）
- 禁止：纯数字（防与任务号混淆）、保留字（admin / system / null / root / api / me 等）、连续空白
- 中文长度按**字符数**计（不是字节）

#### 3.4.2 任务序号规则（**定**）

- 格式 XS-0001，**全局自增**，4 位起步，超过 9999 自动进位（XS-10000）
- 由 PostgreSQL 序列生成，**绝不复用**（删掉的任务号不回收）
- 用户**不可自定义**序号（防钓鱼：XS-0001 和 XS-000l 混淆）

#### 3.4.3 中文检索（**定**）

PostgreSQL 默认分词不认中文。方案：
- **MVP**：用 pg_trgm 扩展 + ILIKE '%关键词%' + GIN 索引（对几万条数据足够快，零额外依赖）
- **后期**：装 zhparser 或 pg_jieba 扩展，换 to_tsvector('chinese', ...)
- 代码里检索走统一函数 search_tasks(q)，**换实现只改一处**

#### 3.4.4 不可判定词表（**定**，发布任务时硬校验）

质量好 / 看得过去 / 尽量 / 差不多 / 优化一下 / 差不多就行 / 快 / 好一点 / 完善 / 美观 / 能用就行 / 酌情 / 视情况

> 命中即拒绝发布，提示：「验收标准必须可机械复核，请写清『谁在什么条件下会红/会绿』」。

## 4. 核心机制

### 4.1 里程碑与决策点（**统一整体型与 Demo 型**）

> 这是本设计**最重要的一次抽象**。用户描述的"整体型"和"Demo 型"不是两种任务，而是**同一条流水线上的不同参数**。

#### 4.1.1 统一模型

~~~
任务 = 有序里程碑列表 [M1, M2, ..., Mn]，每个 Mi 有：
   · bounty_ratio（赏金占比，Σ = 100%）
   · is_decision_gate（是否决策点）

整体型（mode=whole）  = 只有 1 个里程碑，is_decision_gate=true（在末尾决策）
Demo 型（mode=staged） = M1 是 demo（is_decision_gate=true），M2..Mn 是剩余（可继续设决策点）
~~~

**这意味着**：Demo 型可以**多级**（你要求的第 4 条）——M1(gate) → M2(gate) → M3(gate) → … 任意级。

#### 4.1.2 认领与推进

1. 任务 open → 任何人（或团队）认领 → 生成 Claim + 全套 ClaimMilestone（全 pending）
2. 认领者在**任务页**对当前里程碑提交 → 该 ClaimMilestone → submitted
3. 发布者审 → approved（进入下一里程碑）或 rejected（退回返工，轮次 +1）
4. 当**所有活跃 Claim** 都到达某个决策点，或**发布者主动**触发决策 → 任务转 reviewing

#### 4.1.3 决策（发布者）

在决策点，发布者可以做：
- **选一个** Claim 继续（select）→ 其余活跃 Claim 转 rejected（**发落选补偿分**）
- **本阶段结算**：按该里程碑的 bounty_ratio 算出阶段赏金，分配给该人/团队
- **结束任务**（M_n 是最后一个里程碑时）→ 进入 delivered → 分配 → 生成码

#### 4.1.4 多里程碑连续承接

Demo 型里，被选中的 Claim 继续做 M2、M3……**中间每过一个决策点就结算一次阶段性赏金**（生成一批码）。

> **注意**：阶段性赏金也走**完成码**（§4.3）。也就是说 Demo 型任务可能**分批生成码**——每次决策点结算生成一批。**这是有意设计**：码是"发布者确认要付这笔钱"的凭据，与阶段一一对应。

#### 4.1.5 超时与到期（**定**）

| 事件 | 处理 |
|---|---|
| 认领后 due_at 到期未交付 | 该 Claim → expired，扣 −max(1, base//2) 声誉；任务若无其他活跃 Claim → 回 open |
| 任务总 deadline 到期仍有活跃 Claim 未完成 | 任务 → expired（终态），活跃 Claim 全部 expired（各自扣分）；发布者可**复制重发** |
| 决策点后无人被选 | 任务 → expired，落选者照发补偿分 |
| 分配后 30 天未核销完 | 任务 → closed，未核销码 → expired；发布者记一条未核销留痕（**不扣声誉**） |

> **超时扫描**由 Huey 定时任务每 **10 分钟**跑一次，幂等（同一超时只处理一次，靠 TaskEvent 去重）。

### 4.2 变更单（ChangeOrder）

**为什么需要**：直接改字段 = 没有留痕、没有约束、可被误操作。变更单让每次改动都**有理由、有前后值、有约束校验**。

| 变更类型 | 允许改什么 | 约束 |
|---|---|---|
| bounty | 总赏金 | **新值 ≥ 已分配总额**（你定的下限）；只允许在 open/claimed/in_progress/reviewing/delivered/allocated 阶段改 |
| deadline | 总期限 | 只能往后延（**缩期需管理组**，防恶意逼单） |
| milestone | 里程碑增删改 | 已 approved 的里程碑不可删；比例和必须仍 = 100% |
| other | 备注类 | 不改状态 |

**发布者可在任意阶段（含分配完成后）修改分配金额** —— 你明确要求的第 2 条。
约束：Σ 分配额 ≤ 当前总赏金；若某分配对应的码**已核销**，该行 locked，不可改。
**改分配 → 重建未核销的码**（旧码作废，新码发给归属人）。

### 4.3 分配与完成码（**定**）

#### 4.3.1 流程

~~~
① 发布者填写分配表（谁 / 多少钱），只填人和金额 —— 看不到码
② 系统生成 N 个码（N = 被分配主体数），每个码只展示给它的归属人
③ 归属人线下联系发布者：「我是 alice，码 X7K9P2M4QW」
④ 发布者在任务页【填写完成码】→ 系统验证 →
     成功：显示「✅ 此码属于 @alice，应支付 ¥500.00」→ 该码核销
     失败：显示「❌ 码无效或已核销」（**不区分"不存在"与"已核销"**，防枚举）
⑤ 所有码核销完 → 任务自动 closed
~~~

#### 4.3.2 关键规则

| 规则 | 说明 |
|---|---|
| 一主体一码 | 分给 N 个主体就生成 N 个码 |
| 发布者不可见码 | **任何发布者身份的接口都不返回码明文**（只有归属人能看自己的） |
| 码不可枚举 | 核销接口失败一律返回同一个错误；限流（每用户每分钟 5 次） |
| 码只核销一次 | status: issued → redeemed，重复提交返回「已核销」 |
| 核销者必须是发布者 | 团队任务时可以是队长（若队长=发布者则同一人） |
| 分配可改 | 已核销的码锁定；未核销的作废重发 |

### 4.4 声誉系统（**全量重做**）

> **总原则：声誉只能由系统写入。** 发布者**只能通过"选中/完成"间接加分**，**没有任何接口能直接设分**。
> 唯一的降分来源是**系统按规则自动判**（超时、无效交付）。管理组的 admin_adjust 也走事件表留痕。

#### 4.4.1 基础分（按难度，沿用原仓库口径 —— **定**）

| 难度 | 基础分 base |
|---|---|
| easy | **1** |
| medium | **3** |
| hard | **6** |
| expert | **10** |

#### 4.4.2 加分规则

| 场景 | 公式 | 举例 |
|---|---|---|
| **个人**完成任务 | +base | expert 完成 → +10 |
| **团队**任务（队长勾选 n 名参与人） | 每人 max(1, round(base × (1 − 0.2×(n−1)))) | base=10：n=1→10，2→8，3→6，4→4，5→2，6→1 |
| **落选者**（提交过有效交付） | +落选分，按难度 **1/2/3/4** | expert 落选 → +4 |
| **阶段性结算**（Demo 型每过一关） | 按**该里程碑**的比例折算：max(1, round(base × ratio/100)) | base=10，M1 占 30% → +3 |

> **落选分（1/2/3/4）修正了原方案的倒挂**：此前"+2 固定"会让"输掉 expert 竞标"比"完成 easy 任务"更划算；现在 easy 落选 1 = easy 完成 1（持平），expert 落选 4 < expert 完成 10（合理）。
> **落选分只在"提交过有效交付"时发放** —— 光点一下认领然后什么都不交，没有分。

#### 4.4.3 扣分规则（**只有系统能扣**）

| 场景 | 公式 | 举例 |
|---|---|---|
| **超时未交付**（认领到期未交） | −max(1, base // 2) | easy −1，medium −1，hard −3，expert −5 |
| **无效交付**（返工轮次用尽仍未通过，或发布者显式判定"无效交付"并填理由） | −base | expert −10 |
| **管理组手动调整** | 任意值，**必须填理由** | 留痕可查 |

**关键设计：发布者不能凭一次不满就扣分。**
- 发布者点「**退回返工**」→ **不扣分**，只计轮次（默认上限 3 轮）
- 轮次用尽仍不通过，或发布者显式点「**判定为无效交付**」（**必填理由**）→ 系统扣 base
- 被扣分方可**提起争议** → 管理组可 admin_adjust 撤销（撤销也留痕）

#### 4.4.4 不产生声誉的事件（**定**）

| 事件 | 声誉 |
|---|---|
| 主动放弃（withdraw） | 0 |
| 任务被发布者**中途取消** | 0（只给补偿金，见 §4.7.3） |
| 争议提起 / 败诉 | 0（记录在案） |
| 被拒命令 | 0 |
| 发布者未核销 | 0（仅留痕） |

> **"只统计正常结束的任务"**：cancelled / expired 的任务**不产生结算分**；但**超时扣分照扣**（那是行为扣分，不是任务结算）。

#### 4.4.5 幂等与对账

- ReputationEvent 有唯一约束（§3.3.13），**重复投递不重复计分**
- 用户表上的 reputation_total 是缓存；提供 python manage.py recalc_stats 对账命令
- **测试必须断言**：任何路径下 user.reputation_total == sum(events.delta)

## 5. 权限系统

### 5.1 角色（**定**）

| 角色 | 说明 | 如何获得 |
|---|---|---|
| user | **默认**。只能接任务、提交、查看 | 注册即得 |
| publisher | 能**发布任务** + 接任务 | **管理组授予** |
| admin | **能改所有东西**、改角色、封禁 | 种子数据（**部署者**）+ 管理组授予 |
| banned | 封禁（is_banned=true，与 role 正交） | 管理组 |

> **管理员 = 把这个站部署到服务器上的人**（你）。第一个 admin 是种子数据；之后**只有 admin 能授予 admin**。

### 5.2 权限矩阵（**定**）

| 动作 | user | publisher | admin |
|---|---|---|---|
| 注册/登录/看资料 | ✅ | ✅ | ✅ |
| 接任务 / 提交 | ✅ | ✅ | ✅ |
| 建团队 / 入队 | ✅ | ✅ | ✅ |
| **发布任务** | ❌ | ✅ | ✅ |
| 改**自己的**任务（含变更单） | ❌ | ✅ | ✅ |
| 分配 / 核销自己任务的码 | ❌ | ✅ | ✅ |
| 取消自己的任务 | ❌ | ✅ | ✅ |
| 看**别人**任务的提交内容 | ❌ | ❌ | ✅ |
| 改**别人**的任务 | ❌ | ❌ | ✅ |
| **改用户角色** | ❌ | ❌ | ✅ |
| **封禁 / 解封** | ❌ | ❌ | ✅ |
| 看审计日志 | ❌ | ❌ | ✅ |
| 撤销声誉扣分（admin_adjust） | ❌ | ❌ | ✅ |

> **注意**：user 与 publisher 都能"看认领列表"，但**都看不到别人的提交内容**（只有发布者能看自己任务的提交，管理组能看全部）。这对应你的第 11 条：「可以看到谁接了，但是看不到具体内容」。

### 5.3 allowed-actions 协议（**硬约束 —— 定**）

**每个任务页的每次渲染，前端都调一次**：

~~~http
GET /api/tasks/XS-0001/allowed-actions
~~~

**响应**（服务端算出来的、当前登录者能做的全部动作）：

~~~json
{
  "task_serial": "XS-0001",
  "task_status": "claimed",
  "viewer": {"id": 12, "username": "alice", "role": "user"},
  "actions": [
    {"key": "submit",   "label": "提交交付", "enabled": true,  "reason": null},
    {"key": "withdraw", "label": "放弃认领", "enabled": true,  "reason": null},
    {"key": "review",   "label": "验收",     "enabled": false, "reason": "仅发布者可验收"},
    {"key": "allocate", "label": "分配赏金", "enabled": false, "reason": "任务尚未进入待分配状态"}
  ]
}
~~~

**规则**：
1. 前端**只渲染** actions，**不做任何 if 判断**
2. enabled=false 的动作**仍返回**（灰显 + 显示 reason），让用户知道为什么不能做
3. 后端的写接口**独立再判一次**（不能信任前端传来的动作名）—— allowed-actions 是**展示用**，不是**授权用**
4. 这套判定与写接口的判定**共用同一个纯函数**，保证两者永不漂移

### 5.4 服务端纯函数 + 测试策略（**硬约束 —— 定**）

~~~python
# apps/tasks/verdict.py  —— 零 IO、零 ORM、零网络
@dataclass(frozen=True)
class Ctx:
    """裁决上下文：全是数据，可以手工构造。"""
    actor_id: int
    actor_role: str
    actor_team_id: int | None
    task_status: str
    task_publisher_id: int
    claim_status: str | None
    claim_user_id: int | None
    quota_used: int
    quota_limit: int
    now: datetime
    due_at: datetime | None

@dataclass(frozen=True)
class Verdict:
    ok: bool
    action: str
    reason: str
    to_status: str | None
    effects: dict

def can_submit(ctx: Ctx) -> Verdict: ...
def can_allocate(ctx: Ctx) -> Verdict: ...
def can_redeem_code(ctx: Ctx) -> Verdict: ...
def can_claim(ctx: Ctx) -> Verdict: ...
# ...每个动作一个纯函数
~~~

**测试要求**：
1. **逐条判据断言**：每个纯函数的每个分支一条断言
2. **定点变异自证**：往判据里注入一个必失败的改动 → 断言**必须变红且点名到具体那条**
   - 红项数必须**恰好等于期望值**（多红少红都算错）
3. **矩阵测试**：角色 × 状态 × 动作 的笛卡尔积全覆盖
4. **缓存对账**：reputation_total == sum(delta) 在所有路径成立

### 7.2 个人中心的信息架构（**定 —— 你要求的"区分两侧"**）

~~~
/me/tasks
├── 接赏侧（我是接赏者）
│   ├── 已接取        ← 进行中，含「去提交」入口
│   ├── 审核中        ← 已提交，等发布者审
│   └── 已完成        ← 已结算
└── 发布侧（我是发布者）
    ├── 已发布        ← 进行中
    ├── 需审核        ← 有提交等我验收  ★ 带红点计数
    └── 已完成        ← 已关闭
~~~

> **提交入口只在任务详情页（/tasks/{serial}）** —— 你明确要求的。
> 个人中心只做**列表 + 跳转**，列表行点进去就是任务详情页。

### 7.3 关键流程（页面视角）

#### 流程 A：个人接单（整体型）

~~~
任务大厅 → 任务详情 → [认领] → 我接了
   → 做完了 → 任务详情 → [提交交付]（贴读数 + 传文件）
   → 发布者验收 → [通过] → 发布者 [分配] → 生成码
   → 我在 /me/codes 看到码 → 线下找发布者
   → 发布者 [填写完成码] → 核销 → 任务关闭
~~~

#### 流程 B：Demo 型多级

~~~
任务详情 → [认领] → 交 M1(demo) → 发布者审
   → 决策点：发布者 [选人] → 落选者得补偿分
   → 被选中者继续 → 交 M2 → 审 → 决策点 → ...
   → 最后一个里程碑 → [分配] → 生成码 → 核销 → 关闭
~~~

#### 流程 C：团队接单

~~~
队长在任务详情 [以团队认领] → 显示「@团队名 接取」
   → 队长 [提交] → 发布者审
   → 通过 → 发布者 [分配] → 码给**队长**
   → 队长在团队页 [分配赏金 + 勾选参与人]
       └─ 提示语：「这里的赏金分发只影响个人资料信息和排行榜，实际具体奖金分发需要队长自行分发」
   → 系统按勾选人数自动算声誉分 → 队长线下分钱
~~~

## 8. 安全

| 面 | 措施 |
|---|---|
| 密码 | Django 内置（PBKDF2/Argon2），**绝不明文/可逆** |
| 会话 | HttpOnly + Secure + SameSite=Lax |
| CSRF | Django 内置中间件，**所有写操作必须带 token** |
| XSS | 模板自动转义；**禁止用 safe 渲染用户内容**；Markdown 渲染用白名单 |
| SQL 注入 | 全部走 ORM；**禁止字符串拼 SQL** |
| 上传 | **随机重命名落盘**（不用原文件名）；类型白名单；大小上限；**存储目录禁止执行权限** |
| 路径穿越 | 上传路径拼接前用 os.path.realpath 校验必须落在 MEDIA_ROOT 内 |
| 枚举防护 | 不存在的 ID 与无权可见的 ID **返回完全一样**的 404（抄 ClawHunt）；码核销失败**不区分原因** |
| 限流 | §4.8 |
| 密钥 | SECRET_KEY、DB_PASSWORD、CODE_HMAC_KEY、CODE_FERNET_KEY 全部走环境变量，**不进仓库** |
| 审计 | django-auditlog 全量；管理组操作必留痕 |
| 依赖 | 定期 pip-audit；镜像固定 digest |
| 备份 | 见 §9.5 |

**已知限制（诚实声明）**：
- **MVP 无邮箱验证** → 无法防"一人多号刷榜"。缓解：管理组可查审计 + 封禁。**正式上线前必须补邮箱验证**。
- **无 2FA** → 管理组账号建议用强密码 + 限制来源 IP。
- **赏金金额由发布者申报** → 榜单可能失真（§4.7.3 已在界面声明）。

## 9. 部署

### 9.1 Docker 编排（**定**）

docker-compose.yml 五个服务：

~~~yaml
services:
  db:       # postgres:16-alpine，挂 volume，只在内网
  redis:    # redis:7-alpine，只在内网
  web:      # Django + gunicorn，暴露 8000（仅内网）
  worker:   # huey 消费者
  nginx:    # 反向代理 + 静态文件，暴露 80/443
~~~

**关键约定**：
- db / redis **不映射宿主机端口**（只在 compose 内网）
- web 只映射到 127.0.0.1:8000，不对外
- 只有 nginx 对外暴露
- 所有密钥走 .env（.env.example 进仓库，.env 不进）
- 数据持久化：db_data、redis_data、media_data、static_data 四个 volume

### 9.2 路径 A：MVP（内网 / 电脑 / 香港 VPS）—— **推荐起步**

**先回答你的问题：用自己电脑搭一个网站，可行吗？**

**可行，而且对内部 MVP 是最省钱的方案。** 但有四个坑要认清：

| 坑 | 说明 | 解法 |
|---|---|---|
| **家庭宽带没有公网 IP**（多数是 CGNAT） | 外面访问不进来 | **Cloudflare Tunnel**（免费）——不用公网 IP、不用端口映射 |
| **运营商封 80/443** | 国内家宽通常封 | 同上，Tunnel 走 443 出站，**不用开入站端口** |
| **IP 会变** | 路由器重启就换 IP | 同上，Tunnel 不受影响 |
| **断电/关机就挂** | 电脑不是服务器 | 内网用无所谓；要长期在线建议换 VPS |

**所以两条子路径，任选**：

**A1：电脑 + Cloudflare Tunnel（免费，最省事）**

~~~
你的电脑（Docker Compose 全套）
    │  出站连接到 Cloudflare
    ▼
Cloudflare Tunnel（cloudflared 容器）
    │
    ▼
https://xuanshang.你的域名.com   ← 有 HTTPS，不用备案，不用公网 IP
~~~

- 成本：**0 元**（域名另算，也可以先用 *.trycloudflare.com 临时域名）
- 优点：不用备案、不用公网 IP、自动 HTTPS、**隐藏源站**
- 缺点：电脑关机就挂；上行带宽是瓶颈（大文件上传慢）

**A2：香港 VPS + Caddy**

~~~
香港 VPS（1核2G 起，约 ¥30-60/月）
    └── Docker Compose（Caddy 自动 HTTPS）
        └── https://你的域名
~~~

- 优点：24 小时在线、带宽好
- 缺点：要花钱；**不用备案**

> **橙云（Cloudflare 代理）在 MVP 建议开** —— 藏源站 IP、免费防 DDoS。
> 注意：免费版**没有大陆节点**，国内访问会绕路（内部用无所谓）。

### 9.3 路径 B：正式上线（大陆 + 备案）

~~~
大陆云服务器（2核4G 起）+ 已备案域名
    └── Nginx（TLS 用 Let's Encrypt 或云厂商证书）
        └── Docker Compose（同上）
~~~

**关键差异**：

| 项 | 路径 A | 路径 B |
|---|---|---|
| 备案 | **不需要** | **必须**（域名 + 服务器在大陆） |
| Cloudflare 橙云 | ✅ 建议开 | ❌ **不要开**（免费版绕海外，反而慢） |
| CDN | 不需要 | 用国内 CDN |
| 反向代理 | Caddy（省事）或 Nginx | **Nginx** |
| 服务器 | 电脑 / 香港 VPS | 大陆云（阿里云/腾讯云） |

> **好消息**：两条路径的 **Django 代码一行都不用改**，只换 deploy/ 下的配置和 .env。

### 9.4 资源建议

| 阶段 | 配置 | 说明 |
|---|---|---|
| MVP（内部，<50 人） | **1核2G / 2核4G** | Django + PG + Redis + Nginx 全塞一台够用 |
| 正式（<1000 人） | **2核4G / 4核8G** | 建议 DB 独立一台 |
| 再往上 | 加只读副本 + 对象存储 + CDN | 见 §11 |

### 9.5 备份与恢复

| 项 | 策略 |
|---|---|
| 数据库 | 每日 pg_dump → 本地保留 7 天 + 异地 30 天 |
| 媒体文件 | rsync 每日同步；**与数据库分开存** |
| 恢复演练 | **每季度一次**，从备份完整恢复一遍（不演练的备份等于没有） |
| 密钥备份 | SECRET_KEY / CODE_* **必须离线备份** —— 丢了码就全废 |

### 9.6 关键配置项（.env.example）

~~~ini
DJANGO_ENV=prod
SECRET_KEY=change-me
DEBUG=false
ALLOWED_HOSTS=xuanshang.example.com

POSTGRES_DB=xuanshang
POSTGRES_USER=xuanshang
POSTGRES_PASSWORD=change-me
DATABASE_URL=postgres://xuanshang:change-me@db:5432/xuanshang

REDIS_URL=redis://redis:6379/0

# 完成码：HMAC 用于核销比对，Fernet 用于向归属人展示明文
CODE_HMAC_KEY=change-me-32bytes
CODE_FERNET_KEY=change-me-fernet

# 上传
MAX_UPLOAD_MB=20
MAX_TASK_UPLOAD_MB=200

# 业务口径（改口径只改这里）
CLAIM_DEADLINE_HOURS=72
MAX_REWORK_ROUNDS=3
CODE_TTL_DAYS=30
~~~

## 12. 风险与已知限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| **一人多号刷榜** | 榜单失真 | MVP 靠管理组封禁；正式版补邮箱验证 |
| **赏金金额不可验证** | 榜不等于真到账 | 界面显著声明（§4.7.3） |
| **发布者不核销** | 任务挂着 | 30 天自动关闭 + 留痕（不扣分） |
| **发布者恶意判定无效交付** | 接赏者被扣分 | 需填理由 + 可提争议 + 管理组可撤销 |
| **团队刷分后退队** | 团队等级虚高 | 退队即扣除其建队后得分（§4.6.3） |
| **中文检索弱** | 搜不准 | MVP 用 trgm；后期换 zhparser |
| **电脑部署断电** | 服务中断 | 内部 MVP 可接受；正式换 VPS |
| **无备案** | 不能在大陆正式运营 | MVP 内网/香港；正式前完成备案 |
| **码泄露** | 他人冒领 | 码只展示给归属人；核销限流；失败不区分原因 |
